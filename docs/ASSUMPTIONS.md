# Допущения и открытые вопросы

Решения, принятые при проектировании скелета. Всё, что помечено ❓, нужно подтвердить.

## Принято по ответам заказчика

- Точка опоры — Предрейс, данные синхронизируются; пользователи общие, регистрация через Предрейс.
- Фронтенд отдельный, разрабатывает другой человек → API-first, `docs/openapi.json`.
- Подпись выполняется в Предрейсе. XML-схему проектируем сами.
- ~1000 записей/сутки.
- `specialist_user_id` обязателен; у ЭПЛ «Водителя+» осмотры подписывает реальный медик/механик ПРЕДРЕЙС.
- Реквизиты в записи фиксируются на момент осмотра (`snapshot`).
- **Подпись электронного журнала** (решение заказчика): подписывает ООО «ПРЕДРЕЙС» как исполнитель. Клиенты выдают ПРЕДРЕЙС МЧД, все подписи идут подписью ПРЕДРЕЙС, медики и механики его сотрудники. Плашка по ТЗ («Файл подписан ЭЦП ООО «ПРЕДРЕЙС»»), доверенности клиентов в журнал не включаются.

## Интеграция с Предрейсом

Реализовано: сервисный токен, справочники (pull), очередь RabbitMQ, асинхронная подпись, определение фазы осмотра.

| № | Вопрос | Статус |
|---|---|---|
| 1 | Как отличить предрейсовый и послерейсовый осмотр | ✅ Решено: `exam_type` (`pre_trip`/`post_trip`) и `title_number` (2, 6; 3 для техконтроля). Противоречие между ними отклоняется. По рейсу приходит до трёх событий — они не конфликтуют (уникальность по рейсу и титулу) |
| 2 | Точные имена полей payload и справочников | ✅ Сверено по образцам Предрейса от 25.10.2026 (`tests/samples/predreis/`), тесты идут на них дословно |
| 3 | Признак вредных факторов | ✅ Принято: у автоматических осмотров «Водителя+» он `null`, запись **создаётся** с признаком «не определялся» (`harmful_factors` необязателен в БД и XSD, в PDF скрыт) ❓ Подтвердить с заказчиком, что это допустимо для журнала |
| 4 | Сертификаты специалистов (стартовые страницы, плашки) | ✅ Метод Предрейса `GET /api/v1/service/certificates` готов (отбор `role`, `user_id`; отзыв не проверяется); в журналах `GET /me/certificates` и `GET /specialists`. ⚠ **Формат JSON не сверен с образцом** (названы только `serial`, `issuer`, `is_valid`), прошу образец ответа. Действующих сертификатов 7 из 29: у остальных нет данных, статус `missing`. Серийный номер `0x…` приводится к виду из подписи ⏳ |
| 5 | Подпись электронного журнала | ✅ Решено заказчиком: журнал подписывает ООО «ПРЕДРЕЙС» как исполнитель (клиенты выдают ПРЕДРЕЙС МЧД, все подписи идут подписью ПРЕДРЕЙС, медики и механики сотрудники ПРЕДРЕЙС). Плашка по ТЗ: «Файл подписан ЭЦП ООО «ПРЕДРЕЙС»», доверенности клиентов в журнал не включаются. Подписывает сертификат пользователя из `JOURNALS_ORG_SIGNER_USER_ID` (**обязателен**, без него журнал не подписывается). `signer_user_id` записей — `specialist_user_id`. ⏳ Нужно указать, чей это пользователь в Предрейсе и есть ли его сертификат в хранилище КриптоПро (виден в методе `certificates`) |
| 6 | Вход пользователей | ✅ Подтверждено: `POST /api/v1/service/users/verify`, токен пользователя живёт **60 минут**. Роли Предрейса: `superadmin, admin, predreise, client, client_service, dispatcher, driver, driver_plus, medic, mechanic, support`. Журналы понимают 7: `predreise` это наш `predreis` (историческое написание, исправлено); `driver`, `driver_plus`, `support` доступа не получают (нет в ТЗ). ❓ Что такое `client_service` и нужен ли ему доступ |
| 7 | Идемпотентность `external_id`, ответ на неизвестный id | ⏳ Уточнить (используется id нашей задачи) |
| 8 | Единицы алкоголя (`alcohol_ppm`) | ⏳ ‰ или mg/L |
| 9 | Исторические рейсы | Рекомендация: вести журнал с даты запуска (`JOURNALS_EPL_IMPORT_FROM`), неполные не импортировать. Решение заказчика |
| 10 | Формат работы организации (ЭПЛ / бумага / гибрид) | ⚠ В Предрейсе такого понятия **нет** (платформа только про ЭПЛ). По умолчанию все организации считаются ЭПЛ. Связано со строкой 17 этой таблицы (где живут бумажные клиенты) ❓ |
| 11 | Создание организаций, водителей и ТС | Предрейс предлагает: создаются только в Предрейсе, журналы только читают. ⚠ Противоречит ТЗ про бумажных клиентов (см. строку 17 этой таблицы) ❓ |
| 12 | Время осмотра | ✅ Предрейс подставляет время подписания титула, если времени нет в блоке осмотра; ранее отклонённые события он публикует заново. Предохранитель `exam_time_missing` остаётся |
| 13 | Исторические рейсы без медпоказателей | Не импортируются (`invalid_payload`, перечень полей); решает отсечка `JOURNALS_EPL_IMPORT_FROM` |
| 14 | Пол водителя | Заполнен у 1 из 36; пустой допустим, в PDF колонка пуста. Менеджер дозаполняет в Предрейсе |
| 15 | Заглушка подписи `AUTO_SIGNATURE` (64 из 978 титулов) | ✅ Для осмотров: запись без файла подписи, `signature_state=placeholder`. Для подписи журналов: отказ. ❓ Имя поля с подписью титула в событии — после образца |
| 16 | Метка времени (TSP) и статус отзыва (OCSP/CRL) | Предрейс: метки нет (нужна служба штампов времени УЦ, обычно платная); проверка отзыва отключена намеренно (у части УЦ зависает на десятки секунд, водитель ждёт). Возможно включить проверку **только для журнальных подписей** (они идут пачкой, не в реальном времени). ТЗ эти данные требует (стр. 21). ❓ Решение заказчика: нужны ли, и готов ли он оплатить услугу УЦ |
| 17 | Где заводятся бумажные клиенты (организации, водители, ТС без ЭПЛ) | ТЗ: «Добавить организацию/водителя/ТС» в журналах, каталог содержит бумажных клиентов «добавленных вручную». Но Предрейс только про ЭПЛ, и бумажных клиентов в нём нет. Предложение: **локальный каталог журналов** для бумажных клиентов с разделением владения (объекты из Предрейса только читаются, локальные только в журналах; при появлении ИНН в Предрейсе объекты связываются), без двойной записи. ❓ Решение заказчика |
| 18 | Уведомления | Предрейс: система уведомлений есть, нужны новые типы; отправителем должен быть сам Предрейс по запросу журналов (пользователи общие). Нужен метод `POST /api/v1/service/notifications`. Предлагаемые типы: журнал ждёт подписи (суперадмину), запрос на удаление (админу, суперадмину), ежедневная сводка по неподписанным (суперадмину) ⏳ |
