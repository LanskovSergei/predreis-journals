# Допущения и открытые вопросы

Решения, принятые при проектировании скелета. Всё, что помечено ❓, нужно подтвердить.

## Принято по ответам заказчика

- Точка опоры — Предрейс, данные синхронизируются; пользователи общие, регистрация через Предрейс.
- Фронтенд отдельный, разрабатывает другой человек → API-first, `docs/openapi.json`.
- Подпись выполняется в Предрейсе. XML-схему проектируем сами.
- ~1000 записей/сутки.
- `specialist_user_id` обязателен; у ЭПЛ «Водителя+» осмотры подписывает реальный медик/механик ПРЕДРЕЙС.
- Реквизиты в записи фиксируются на момент осмотра (`snapshot`).
- **Подпись электронного журнала** (решение заказчика): подписывает ООО «ПРЕДРЕЙС» как исполнитель. Клиенты выдают ПРЕДРЕЙС МЧД, все подписи идут подписью ПРЕДРЕЙС, медики и механики его сотрудники. Плашка по ТЗ («Файл подписан ЭЦП ООО «ПРЕДРЕЙС»»), доверенности клиентов в журнал не включаются.
- **Общий каталог организаций** (решение заказчика): в журналах ведётся каталог всех организаций, с которыми работает ПРЕДРЕЙС. Организации из платформы приходят из ПРЕДРЕЙС, бумажные клиенты добавляются вручную; по сути все клиенты гибридные. Водителей и ТС вручную можно добавлять и к организациям из платформы. Когда организация, добавленная вручную, появляется в ПРЕДРЕЙС, карточки **объединяются автоматически**: организация по ИНН, водитель по ФИО и дате рождения, ТС по госномеру; наш идентификатор и все записи сохраняются, реквизиты берутся из платформы, поля журналов (договор, контакты, СНИЛС, сроки ВУ, диагностическая карта, примечание) остаются.
- Допущение (ждёт подтверждения): править и удалять ручные карточки могут Предрейс, Админ, СА; карточку, по которой есть записи, не удаляют, а делают неактивной. Реквизиты карточек из платформы в журналах не меняются.
- **Значок «на ЭПЛ / на бумаге»** (решение заказчика): ставится автоматически. Организация «на ЭПЛ», если она есть в платформе и прошла этап «реквизиты для ЭПЛ / МЧД»; если её нет в платформе или МЧД не оформлена — «на бумаге». От этого же признака зависит доступ клиента и диспетчера к журналам.
- **Кто запускает подпись ручной записи** (ждёт решения заказчика): по ТЗ — сам специалист из записи. Предрейс технически может подписывать и по запросу менеджера, поэтому сделана настройка `JOURNALS_MANAGERS_CAN_SIGN_RECORDS` (по умолчанию выключена): при включении Предрейс, Админ и СА запускают подпись, подписантом уходит специалист из записи, кто запустил — в аудите.

## Интеграция с Предрейсом

Реализовано: сервисный токен, справочники (pull), очередь RabbitMQ, асинхронная подпись, определение фазы осмотра.

| № | Вопрос | Статус |
|---|---|---|
| 1 | Как отличить предрейсовый и послерейсовый осмотр | ✅ Решено: `exam_type` (`pre_trip`/`post_trip`) и `title_number` (2, 6; 3 для техконтроля). Противоречие между ними отклоняется. По рейсу приходит до трёх событий — они не конфликтуют (уникальность по рейсу и титулу) |
| 2 | Точные имена полей payload и справочников | ✅ Сверено по образцам Предрейса от 25.10.2026 (`tests/samples/predreis/`), тесты идут на них дословно |
| 3 | Признак вредных факторов | ✅ Принято: у автоматических осмотров «Водителя+» он `null`, запись **создаётся** с признаком «не определялся» (`harmful_factors` необязателен в БД и XSD, в PDF скрыт) ❓ Подтвердить с заказчиком, что это допустимо для журнала |
| 4 | Сертификаты специалистов (стартовые страницы, плашки) | ✅ Метод `GET /api/v1/service/certificates` (отбор `role`, `user_id`), **формат сверен с образцом**: ФИО частями, владелец `cert_cn`, серийный номер `0x…` (приводится к виду из подписи), сроки «ДД.ММ.ГГГГ» (последний день срока действует), `is_valid`. Действующих сертификатов 7 из 29: у остальных данных нет, статус `missing`. Отзыв не проверяется |
| 5 | Подпись электронного журнала | ✅ Решено заказчиком и реализовано Предрейсом: журнал подписывает **КЭП организации** ООО «ПРЕДРЕЙС» (`sign_as=organization`, без пользователя, с `requested_by_user_id`). Подписи специалистов — по `signer_user_id`. Плашка по ТЗ, доверенности клиентов в журнал не включаются |
| 6 | Вход пользователей | ✅ Подтверждено Предрейсом: человек вводит почту и пароль ПРЕДРЕЙС в интерфейсе журналов, журналы получают токен через `POST /api/v1/auth/login` и проверяют его `POST /api/v1/service/users/verify`; готовых токенов Предрейс не выдаёт. Токен живёт 60 минут. Роли: `superadmin, admin, predreise, client, client_service, dispatcher, driver, driver_plus, medic, mechanic, support`; журналы понимают 7, `predreise` — наш `predreis` ❓ что такое `client_service` |
| 7 | Идемпотентность `external_id`, ответ на неизвестный id | ⏳ Уточнить (используется id нашей задачи) |
| 8 | Единицы алкоголя (`alcohol_ppm`) | ⏳ ‰ или mg/L |
| 9 | Исторические рейсы | Рекомендация: вести журнал с даты запуска (`JOURNALS_EPL_IMPORT_FROM`), неполные не импортировать. Решение заказчика |
| 10 | Формат работы организации (значок «на ЭПЛ / на бумаге») | ✅ Решено заказчиком: по данным платформы. Нужно поле **`epl_ready: bool`** в `GET /api/v1/service/catalogs/organizations` (`true`, когда реквизиты для ЭПЛ подтверждены и МЧД оформлена) и смена `updated_at` при его изменении. Журналы уже это обрабатывают; пока поле не приходит, организации из платформы считаются «на ЭПЛ», ручные «на бумаге» ⏳ |
| 11 | Создание организаций, водителей и ТС | ✅ Решено заказчиком: общий каталог. Карточки из ПРЕДРЕЙС читаются и синхронизируются, ручные создаются в журналах; двойной записи нет: при появлении в ПРЕДРЕЙС ручная карточка объединяется с платформенной (`predreis_id`), её реквизиты дальше ведёт ПРЕДРЕЙС |
| 12 | Время осмотра | ✅ Предрейс подставляет время подписания титула, если времени нет в блоке осмотра; ранее отклонённые события он публикует заново. Предохранитель `exam_time_missing` остаётся |
| 13 | Исторические рейсы без медпоказателей | Не импортируются (`invalid_payload`, перечень полей); решает отсечка `JOURNALS_EPL_IMPORT_FROM` |
| 14 | Пол водителя | Заполнен у 1 из 36; пустой допустим, в PDF колонка пуста. Менеджер дозаполняет в Предрейсе |
| 15 | Заглушка подписи `AUTO_SIGNATURE` (64 из 978 титулов) | ✅ Для осмотров: запись без файла подписи, `signature_state=placeholder`. Для подписи журналов: отказ. ❓ Имя поля с подписью титула в событии — после образца |
| 16 | Метка времени (TSP) и статус отзыва (OCSP/CRL) | Предрейс: метки нет (нужна служба штампов времени УЦ, обычно платная); проверка отзыва отключена намеренно (у части УЦ зависает на десятки секунд, водитель ждёт). Возможно включить проверку **только для журнальных подписей** (они идут пачкой, не в реальном времени). ТЗ эти данные требует (стр. 21). ❓ Решение заказчика: нужны ли, и готов ли он оплатить услугу УЦ |
| 17 | Где заводятся бумажные клиенты | ✅ Решено: локальный каталог журналов с автоматическим объединением (см. «Принято по ответам заказчика»). Автозаполнение реквизитов по ИНН и ежемесячная сверка с ЕГРЮЛ ждут выбора сервиса ❓ |
| 18 | Уведомления | Предрейс: система уведомлений есть, нужны новые типы; отправителем должен быть сам Предрейс по запросу журналов (пользователи общие). Нужен метод `POST /api/v1/service/notifications`. Предлагаемые типы: журнал ждёт подписи (суперадмину), запрос на удаление (админу, суперадмину), ежедневная сводка по неподписанным (суперадмину) ⏳ |

## Электронный журнал (этап 2)

| № | Вопрос | Принято |
|---|---|---|
| 1 | Подпись записей из ЭПЛ в ZIP | Кладётся как `epl-title.sig/.tsp` без `signedFile`; нет `signature_b64` — запись идёт без файла подписи ❓ |
| 2 | Сертификаты УЦ и OCSP | Не включены: Предрейс их не отдаёт ❓ |
| 3 | Доступ к ZIP | Только Предрейс, Админ, СА; в `record.xml` медицинские показатели не скрыты, в PDF скрыты ❓ |
| 4 | Audit log | Подмножество цепочки на момент отправки на подпись; хеш входит в подписанный `journal.xml`, отдельной подписи нет ❓ |
| 5 | Размер | Контейнер собирается в памяти; для ~1–2 тыс. записей на журнал достаточно, потоковая сборка — при росте |
| 6 | `epl_details` в XML | Не включены (вопрос 3 из `xml-schema.md`) ❓ |
