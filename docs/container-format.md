# ZIP-контейнер электронного журнала

Электронный журнал (документ типа 2) — ZIP-архив, подписанный УКЭП организации (ПРЕДРЕЙС). Формат: `1.0`.
Сборку выполняет `app/modules/ejournal/builder.py`, чистую логику (сборка ZIP, проверка) —
`app/modules/ejournal/container.py`. Скачать контейнер могут только Предрейс, Админ и СА (`ejournal:view`);
клиенты получают лишь PDF-выгрузки со скрытыми медицинскими показателями.

## Жизненный цикл

```
Сформировать ──► DRAFT ──Отправить──► AWAITING_SIGNATURE ──Подписать (СА)──► SIGNED
                  │                        │
                Отмена                  Отклонить ──► REJECTED (пакет расформирован, записи свободны)
```

1. **Сформировать** — подсчёт подходящих записей (статус Б, не на удалении, не в другом журнале), ничего не резервируется.
2. **Отправить** — записи резервируются; собираются `journal.xml`, выгрузка аудита, человекочитаемый PDF для СА
   (до подписи, без плашки); хеши фиксируются в `e_journals.package`.
   Готовые файлы записей берутся **байт в байт** из подписанных документов: перегенерация сломала бы подпись.
   Хеш каждого файла сверяется с зафиксированным при подписи записи (`storage_integrity` при расхождении).
3. **Подписать (СА)** — Предрейс подписывает именно тот `journal.xml`, который был подготовлен (его хеш
   перепроверяется), PDF перерисовывается с синей плашкой, собирается ZIP и проходит самопроверку
   (`verify_container`), записи становятся типа В (неизменяемыми, в том числе триггером БД).
4. **Отклонить** — записи освобождаются, подготовленные файлы журнала удаляются; оригиналы подписанных записей остаются.

## Состав

| Путь | Назначение (`role` в манифесте) |
|---|---|
| `manifest.xml` | реестр файлов: путь, размер, SHA-256, роль, `recordId`, `signedFile` (какая подпись к какому файлу) |
| `journal.xml` | машиночитаемый журнал, `journal-xml` |
| `journal.xml.sig` | откреплённая УКЭП организации на `journal.xml`, `journal-signature` |
| `journal.xml.tsp` | метка доверенного времени к подписи (если выдана), `journal-timestamp` |
| `journal.pdf` | человекочитаемый журнал с плашкой подписи, `journal-pdf` |
| `records/<id>/record.xml` | запись, `record-xml` |
| `records/<id>/record.pdf` | запись для чтения, `record-pdf` |
| `records/<id>/record.xml.sig`, `.tsp` | подпись специалиста и метка времени, `record-signature`, `record-timestamp` |
| `records/<id>/epl-title.sig`, `.tsp` | для записей из ЭПЛ: подпись титула (подписывает титул, не `record.xml`; `signedFile` не указан) |
| `audit/audit-log.json` | выгрузка аудита по записям журнала на момент отправки, `audit-log` |
| `README.txt` | версия формата, порядок проверки, `readme` |

Сертификаты УЦ и ответы OCSP в контейнер пока не включаются: Предрейс в ответе подписи отдаёт только
данные сертификата и статус OCSP.

## Целостность

- `journal.xml` содержит SHA-256 каждого файла записи и выгрузки аудита, а значит подпись организации покрывает их все.
- Манифест не подписывается отдельно: его цель — сверка состава и реестр; доверие задаёт подпись `journal.xml`.
- Выгрузка аудита — подмножество глобальной хеш-цепочки: у каждой записи свой `prev_hash`, хеш пересчитывается
  независимо (`verify_audit_export`); `chainHead` — голова полной цепочки на момент выгрузки.
- Сборка детерминирована (фиксированные даты в ZIP, сортировка путей): повторная сборка тех же данных даёт тот же ZIP.
- Проверка архива (`verify_container`) защищается от zip-бомб, `..`, абсолютных и дублирующихся путей.

## Проверка вручную

См. `README.txt` внутри контейнера. Криптографическую проверку `.sig` выполняет СКЗИ (КриптоПро CSP);
сервис проверяет всё остальное — состав, хеши, схемы и согласованность ссылок.
