# Руководство для разработчика фронтенда

Сервис «Электронные журналы» — API на FastAPI. Всё, что нужно интерфейсу, описано здесь; точные схемы —
в [openapi.json](openapi.json) и TypeScript-типах [frontend/api.d.ts](frontend/api.d.ts).

## 1. Быстрый старт

- Базовый адрес API: `https://<домен журналов>/api/v1`. Swagger — `/docs`.
- Типы: `docs/frontend/api.d.ts` (создаётся командой `make types`, то есть
  `npx openapi-typescript docs/openapi.json -o docs/frontend/api.d.ts`). Пример использования с
  `openapi-fetch`: `createClient<paths>({ baseUrl })`.
- **CORS:** разрешены только адреса из `JOURNALS_CORS_ORIGINS`, методы GET/POST/PATCH/DELETE и заголовки `Authorization`,
  `Content-Type`, `X-Request-ID`; cookies не используются (токен в заголовке). Нужен другой заголовок — скажите.
- **Локальный стенд с подставным ПРЕДРЕЙСом** (чтобы работать без боевых систем) — раздел 12.
- Все даты и время в JSON — ISO 8601. Даты фильтров и отображение — по московскому времени
  (`Europe/Moscow`), момент осмотра хранится с часовым поясом.

## 2. Вход

Учётные записи общие с ПРЕДРЕЙСом: пользователь вводит ту же почту и пароль.

```http
POST /api/v1/auth/login
{"email": "user@example.ru", "password": "..."}
```

Ответ `200`: `{access_token, token_type: "bearer", expires_in, user: {id, full_name, role, organization_id}, permissions: [...]}`.
Дальше на **каждый** запрос заголовок `Authorization: Bearer <access_token>`.

| Ответ | Что показать |
|---|---|
| `401 invalid_credentials` | «Неверная почта или пароль» |
| `403 journals_disabled` | «Доступ к журналам не предоставлен. Обратитесь к администратору» (флаг включает суперадмин в ПРЕДРЕЙСе) |
| `403 role_unsupported` | «Ваша роль не поддерживается журналами» |
| `429 too_many_requests` | «Слишком много неудачных попыток, повторите позже» (считаются только неудачные: 10 за 5 минут по одной почте, 50 с одного адреса; успешные входы лимит не расходуют) |
| `502 upstream_error` | «ПРЕДРЕЙС временно недоступен» |

- **Срок жизни токена задаёт ПРЕДРЕЙС** (`expires_in`, сейчас 60 минут). Обновления токена нет: при `401 unauthorized`
  на любом запросе отправляйте пользователя на экран входа.
- Токен проверяется на сервере у ПРЕДРЕЙСа (ответ кэшируется на 30 с): **отключение доступа вступает в силу в течение
  полминуты**, и тогда следующий запрос вернёт `403 journals_disabled`.
- Хранить токен лучше в памяти (или `sessionStorage`), не в `localStorage`.
- `GET /api/v1/me` возвращает профиль и **список прав** (`permissions`), по нему включайте разделы интерфейса.

## 3. Формат ошибок

Все ошибки одного вида:

```json
{"error": {"code": "signing_in_progress", "message": "Запись отправлена на подпись", "details": null}}
```

- `code` — стабильный машинный код (по нему выбирайте поведение), `message` — текст на русском (можно показывать).
- `422 request_invalid`: `details` — массив `{loc: [...], msg, type}` (ошибки полей: `loc[-1]` — имя поля).
- `422 validation_failed` и другие `422` с кодом: бизнес-проверка (например, `driver_invalid`: водитель не из этой организации).
- `409` — действие недопустимо в текущем состоянии записи. Обновите запись и пересоберите кнопки.

Коды, которые стоит обработать особо:

| Код | HTTP | Когда |
|---|---|---|
| `unauthorized` | 401 | нет/просрочен токен → экран входа |
| `journals_disabled` | 403 | доступ к журналам выключен |
| `permission_denied` | 403 | роли не хватает прав на действие |
| `not_epl_org` | 403 | клиент/диспетчер организации не на ЭПЛ |
| `not_found` | 404 | записи нет или она недоступна пользователю |
| `signing_in_progress` | 409 | запись отправлена на подпись: менять и удалять нельзя |
| `note_not_empty` | 409 | запись с примечанием подписать нельзя: сначала «Снять примечание» |
| `not_record_specialist` | 403 | подписать запись может только её специалист |
| `record_immutable`, `epl_immutable`, `in_journal` | 409 | запись подписана, из ЭПЛ или уже в журнале |
| `already_signed`, `deletion_pending`, `invalid_status` | 409 | действие не подходит текущему статусу |
| `driver_invalid`, `vehicle_invalid`, `specialist_invalid`, `specialist_required` | 422 | неверные ссылки в теле запроса |
| `record_xml_invalid` | 422 | в данных записи нет обязательного значения (текст ошибки покажите пользователю) |
| `signature_meta_missing` | 409 | в подписи нет данных сертификата: запись в журнал не попадёт |
| `storage_integrity` | 409 | файл записи в хранилище не совпадает с зафиксированным (обратитесь в поддержку) |
| `too_many_requests` | 429 | слишком много неудачных попыток входа |
| `upstream_error` | 502 | ПРЕДРЕЙС недоступен |
| `not_implemented` | 501 | функция в разработке (OCR) |

Полный перечень кодов (48) приведён в приложении Б.

## 4. Роли и разделы интерфейса

Права приходят в `permissions` (`GET /me`). Соответствие ролям (из ТЗ):

| Раздел | client, dispatcher | medic | mechanic | predreis | admin | superadmin |
|---|---|---|---|---|---|---|
| Архив медосмотров | свой, без показателей | да | нет | да | да | да |
| Архив техконтроля | свой | нет | да | да | да | да |
| Создание записей | нет | медосмотр | техконтроль | оба | оба | оба |
| Подпись записей | нет | свои медосмотры | свой техконтроль | нет | нет | нет |
| Выгрузка PDF | да (своя организация) | да | да | да | да | да |
| Электронные журналы: формирование | нет | нет | нет | да | да | да |
| Электронные журналы: подпись | нет | нет | нет | нет | нет | да |
| Запросы на удаление: создать | нет | нет | нет | да | нет | нет |
| Запросы на удаление: решить | нет | нет | нет | нет | да | да |
| Справочники (организации, водители, ТС) | нет | нет | нет | да | да | да |
| Сертификаты специалистов (плашки, список для фильтра) | нет | свои | свои | да | да | да + счётчики |
| Статистика стартовой | нет | да | да | да | да | да |

«Клиент» и «диспетчер» видят только **свою ЭПЛ-организацию** и только **подписанные** записи; в ответе для них нет
медицинских показателей (поля отсутствуют целиком, а не скрыты).

## 5. Записи архива

Запись — строка архива. Поля, которые нужны интерфейсу:

- `status`: `unsigned` (А, можно править) → `signed` (Б, подписана специалистом) → `in_journal` (В, в подписанном
  электронном журнале, неизменяема).
- `source`: `manual`, `ocr`, `epl` (из электронного путевого листа: не редактируется и не удаляется никем).
- `has_note` и `note`: если примечание есть, **выделите строку цветом**; такую запись подписать нельзя.
  Сервер сам добавляет примечание при спорных данных (одометр меньше предыдущего, подозрительная дата рождения);
  после проверки пользователь нажимает «Снять примечание».
- `signature`: `{cert_serial, cert_subject, cert_valid_from, cert_valid_to, signed_at}` для колонки подписи (или `null`).
- `signing_status` и `signing_error` — состояние подписи (раздел 7).
- `deletion_pending`, `in_journal_reserved`: запись поставлена на удаление / зарезервирована в журнале.
- **`actions`** — список разрешённых пользователю действий над строкой: `edit`, `clear_note`, `delete`, `sign`,
  `request_deletion`, `delete_signed`. **Рисуйте кнопки строго по этому списку** и не вычисляйте права сами:
  сервер учитывает роль, статус, источник, примечание, подпись и идущую подпись.
- Медосмотр, показатель «вредные факторы» (`harmful_factors`) может быть `null`: признак не определялся
  (автоматические осмотры «Водителя+»). Это не то же самое, что «отсутствуют»; показывайте «не определялись».

Для клиента/диспетчера медосмотр приходит в сокращённом виде: общие поля (`id`, `status`, `source`, `waybill_kind`,
`performed_at`) и `driver_full_name`, `driver_birth_date`, `driver_gender`, `specialist_name`, `phase`, `result`,
`signature`. Показателей здоровья, примечания и `actions` в нём нет.

### Список

`GET /medical/records`, `GET /technical/records`. Параметры:

| Параметр | Описание |
|---|---|
| `page` (≥1), `page_size` | страница (по умолчанию 10, максимум 100); ответ `{items, total, page, page_size}` |
| `organization_id`, `specialist_user_id` | по организации / медику или механику |
| `date_from`, `date_to` | `ГГГГ-ММ-ДД`, включительно, по московским суткам |
| `result` | `admitted` / `not_admitted` |
| `has_note` | `true` — только с примечанием |
| `is_signed` | `true` — подписанные и в журнале, `false` — неподписанные («на подпись») |
| `driver_id` / `vehicle_id` | записи одного водителя / ТС (быстро; используйте при выборе из справочника) |
| `driver_name` / `plate` | поиск по подстроке, **от 3 символов** (`plate` ищет госномер в самой записи) |
| `vehicle` | техконтроль: поиск по марке, модели и госномеру ТС из справочника (от 3 символов), например `газон next` |

Сортировка фиксирована: самые новые первыми. Для «На подпись» у медика: `is_signed=false&specialist_user_id=<мой id>`.

### Создание и изменение

`POST /medical/records`, `POST /technical/records` (`201`), `PATCH .../{id}`. Важно:

- `performed_at` — **с часовым поясом** (`2026-10-14T08:20:00+03:00`), без пояса вернётся `422`.
- Медик/механик создают записи только от себя (`specialist_user_id` не нужен). Менеджеры, админ и суперадмин обязаны
  указать `specialist_user_id`.
- **«Стандартное время»** (ТЗ: для первой записи время вводят вручную, дальше подставляется прежнее):
  `GET /medical/records/standard-time?driver_id=…&phase=pre|post` и `GET /technical/records/standard-time?vehicle_id=…`
  возвращают `{time: "ЧЧ:ММ" | null, performed_at, record_id}` по последней записи из бумажного путевого листа.
  `null` значит записей ещё не было: поле времени пустое, пользователь вводит вручную.
- Создание «на период» (несколько дат) сервер пока не поддерживает: для диапазона отправляйте запросы по каждой дате.
- Изменять можно только запись `unsigned` из `manual`/`ocr` и только пока она не отправлена на подпись.

## 6. Справочники

`GET /catalog/organizations`, `/catalog/drivers`, `/catalog/vehicles` (`q` — поиск, `organization_id`, `page`, `page_size`;
только менеджерские роли). Данные приходят из ПРЕДРЕЙСа и **создаются и меняются только там**; для выпадающих списков
используйте поиск по `q` с подгрузкой, а не загрузку всего списка. Пол и дата рождения водителя могут быть пустыми.
Организации отсортированы по алфавиту **без правовой формы** (ИП, ООО, АО и т. п.) и кавычек, как требует ТЗ.

### Добавление и правка (Предрейс, Админ, СА)

Каталог общий: организации из ПРЕДРЕЙС и добавленные вручную (бумажные клиенты). Поле **`origin`**: `platform` или
`manual` (откуда карточка), фильтр `GET /catalog/organizations?origin=manual`. **Значок «на ЭПЛ / на бумаге»** ставьте
по `work_format` (`epl` или `paper`): его вычисляет сервер по данным платформы (пройден ли этап «реквизиты для ЭПЛ / МЧД»).

| Действие | Запрос | Правила |
|---|---|---|
| Добавить организацию | `POST /catalog/organizations` | ИНН проверяется по контрольным разрядам (10 или 12 цифр) и уникален во всём каталоге: при совпадении `409 organization_exists`, в `details.organization_id` id существующей карточки. Срок договора по умолчанию 31.12.2026 |
| Добавить водителей | `POST /catalog/drivers {"drivers": [...]}` | до 10 за раз, к любой организации (и из ПРЕДРЕЙС), СНИЛС проверяется; повтор ФИО и даты рождения в организации — `409 driver_exists` с `details.index`; всё или ничего |
| Добавить ТС | `POST /catalog/vehicles {"vehicles": [...]}` | до 10 за раз; госномер приводится к одному виду (пробелы, регистр, латиница), повтор в организации — `409 vehicle_exists` |
| Изменить | `PATCH /catalog/{organizations,drivers,vehicles}/{id}` | у карточек из ПРЕДРЕЙС реквизиты не меняются (`409 managed_by_predreis`, в `details.fields` какие поля), можно менять только поля журналов: договор, контакты, СНИЛС, сроки ВУ, диагностическую карту, примечание |
| Удалить | `DELETE …/{id}` | только ручные карточки без связанных данных; иначе `409 in_use`: сделайте карточку неактивной (`PATCH {"is_active": false}`) |

Когда организация, добавленная вручную, регистрируется в ПРЕДРЕЙС, карточки объединяются автоматически при синхронизации:
`id` и записи сохраняются, `origin` становится `platform`, реквизиты начинают приходить из ПРЕДРЕЙС.

## 6.1. Сертификаты специалистов

Данные берутся из Предрейса (метод `certificates`), кэшируются на минуту. **Отзыв сертификата не проверяется**
(`revocation_checked: false`): статус считается по сроку действия и признаку действительности Предрейса.

| Метод | Кому | Что отдаёт |
|---|---|---|
| `GET /me/certificates` | медик, механик | свои сертификаты для стартовой страницы: `status`, `valid_to`, список `certificates` |
| `GET /specialists?role=medic\|mechanic` | Предрейс, Админ, СА | специалисты с сертификатом для плашек и для выпадающего списка фильтра «ФИО медика/механика» (`user_id` подставляется в `specialist_user_id`); у СА дополнительно `records` |

Статус сертификата (`status`): `active` (действует), `expired` (срок прошёл или Предрейс отметил недействительным),
`missing` («нет действующего сертификата»: в хранилище КриптоПро его нет). **Не пишите «истёк» для `missing`:**
по данным нельзя отличить истёкший сертификат от удалённого (сейчас действующих только 7 из 29). Если
`expiring_soon: true`, покажите предупреждение (до конца срока 30 дней и меньше). Серийный номер приходит в виде
hex без `0x` (как в подписи), `owner` это владелец по сертификату, `issuer` удостоверяющий центр. У одного
специалиста может быть несколько сертификатов, в `status` и `valid_to` попадает лучший.

Счётчики `records` (`to_sign`, `signed`, `total`) отдаются **только суперадмину** (по ТЗ они стоят рядом с сертификатами
у СА); у остальных ролей поле `null`. Если Предрейс не ответил, `GET /specialists` всё равно возвращает специалистов и счётчики,
но `certificates_available: false`, а сертификаты пустые: покажите «данные о сертификатах недоступны». `GET /me/certificates`
в этом случае вернёт `502`.

## 7. Подпись записей (асинхронная)

Подписывает ПРЕДРЕЙС личным сертификатом специалиста, это не мгновенно (обычно до нескольких десятков секунд).

1. Пользователь выделяет строки с кнопкой `sign` и нажимает «Подписать» →
   `POST /medical/records/sign` (`/technical/records/sign`), тело `{"record_ids": ["..."]}`, **не более 50** за раз.
2. Ответ `200`: `{signed, failed, results: [{record_id, ok, code, message}]}`. `ok: true` значит «принято в очередь», а не «подписано».
   Для `ok: false` покажите `message` у строки.
3. Дальше **опрашивайте** список или запись раз в 5–10 секунд, пока `signing_status` не станет `null`:
   - `queued` / `pending` — идёт подпись: показывайте индикатор, **кнопок нет** (`actions: []`);
   - `failed` — отказ, причина в `signing_error` (например, «нет сертификата»); кнопки вернулись, можно исправить и повторить;
   - `null` и `status: "signed"` — готово, в `signature` данные сертификата.
4. Подпись не пройдёт, если у записи есть примечание, она не ваша или уже подписана: ответ придёт сразу в `results`.
5. Если на сервере включена настройка `JOURNALS_MANAGERS_CAN_SIGN_RECORDS`, кнопка `sign` появляется и у Предрейс, Админа, СА:
   они запускают подпись за специалиста записи. Рисуйте кнопку по `actions`, отдельной логики на фронтенде не нужно.

## 8. Удаление

- Неподписанную запись удаляют `DELETE /{kind}/records/{id}` (`204`). **Выбранные галочками:**
  `POST /{kind}/records/delete {"record_ids": [...]}` (до 50), ответ `{deleted, failed, results: [{record_id, ok, code, message}]}`:
  подписанные, чужие и несуществующие записи не удаляются, причина приходит по каждой.
- Подписанную нельзя удалить напрямую: менеджер ПРЕДРЕЙС создаёт запрос
  `POST /{kind}/records/{id}/deletion-request {reason}` (`201`), Админ и Суперадмин решают в разделе запросов:
  `GET /deletion-requests`, `POST /deletion-requests/{id}/approve|reject`.
  Админ/СА могут удалить подписанную запись сразу: `DELETE /records/{kind}/{id}/signed`.
- Записи из ЭПЛ и записи в журнале не удаляются никем.

## 9. Выгрузка PDF

`POST /exports/medical` / `/exports/technical`, тело: `{organization_id, date_from, date_to, record_ids?}`
`organization_id` обязателен для менеджерских ролей (отчёт всегда по одной организации; без него `422`), даже если
передан список `record_ids`; для клиента/диспетчера организация подставляется автоматически. Ответ — файл `application/pdf`:

```ts
const res = await fetch(url, { method: "POST", headers, body });
const name = decodeURIComponent(res.headers.get("content-disposition")!.split("UTF-8''")[1]);
const blob = await res.blob();   // имя: «Отчёт о медосмотрах ПРЕДРЕЙС_с 01.10.2026 по 31.10.2026.pdf»
```

В выгрузке не больше 5000 строк (иначе `422`: сузьте период); медицинские показатели в PDF скрыты (`N/A`).
Выгрузка месяца одной организации занимает около полсекунды, крупная до нескольких секунд.

## 10. Электронные журналы

Только менеджерские роли (`predreis`, `admin`, `superadmin`); подписывает только `superadmin`.

| Шаг | Запрос | Статус журнала после |
|---|---|---|
| «Сформировать» | `POST /ejournals {kind, organization_id, period_from, period_to}` (`201`) | `draft` (в ответе `record_count`) |
| Отмена | `DELETE /ejournals/{id}` | журнал удалён |
| «Отправить на подпись» | `POST /ejournals/{id}/submit` | `awaiting_signature` |
| Просмотр содержимого | `GET /ejournals/{id}/preview` (PDF) | |
| «Подписать» (СА) | `POST /ejournals/{id}/sign` | `signing`, затем `signed` |
| «Отклонить» (СА) | `POST /ejournals/{id}/reject {reason}` | `rejected` (записи снова свободны) |
| Скачать ZIP | `GET /ejournals/{id}/download` | только после `signed`, иначе `404` |

- После «Подписать» журнал в статусе `signing`; опрашивайте `GET /ejournals/{id}` раз в 5–10 с. Итог: `signed`
  либо возврат в `awaiting_signature` с текстом в `sign_error` (кнопку «Подписать» можно нажать снова).
- Пока журнал `signing`, «Отклонить» недоступно (`409`).
- PDF с заголовком `Authorization` нельзя открыть ссылкой: загрузите `fetch` → `blob` → `URL.createObjectURL` и покажите в `<iframe>`.
- Записи, попавшие в подписанный журнал, получают статус `in_journal`.

## 11. Статистика стартовой

`GET /stats/overview`: у медика и механика только `medical` либо `technical` (`{to_sign, signed, total}` по их записям);
у менеджеров дополнительно `organizations` и `drivers` (`{active, total}`).

## 12. Локальный стенд

Без доступа к ПРЕДРЕЙСу можно поднять весь контур: подставной ПРЕДРЕЙС, API, воркер, потребитель очереди.

```bash
make dev-stack            # нужны запущенные PostgreSQL, Redis и RabbitMQ
# или, если установлен Docker:
docker compose -f docker-compose.dev.yml up --build
```

Откройте `http://127.0.0.1:8000/docs`. Пользователи (пароль у всех `password`):

| Почта | Роль | Примечание |
|---|---|---|
| `superadmin@example.ru` | superadmin | подписывает журналы |
| `predreis@example.ru` | predreis | менеджер |
| `medic@example.ru` | medic | подпись проходит |
| `mechanic@example.ru` | mechanic | |
| `client@example.ru` | client | организация «ООО Тест Транс» |
| `noaccess@example.ru` | predreis | доступа нет: вход вернёт отказ |

Управление подставным ПРЕДРЕЙСом (`http://127.0.0.1:9000`):

- `POST /_dev/publish {"waybills": 3}` — опубликовать осмотры (по каждому рейсу: предрейсовый, послерейсовый, техконтроль);
  `{"old_technical_without_time": true}` добавит событие, которое должно быть отклонено.
- `POST /_dev/sign-mode/normal|fail|placeholder` — подпись проходит / отказывает / возвращает заглушку `AUTO_SIGNATURE`.
- `GET /_dev/users` — список пользователей.

## Приложение Б. Коды ошибок

| Код | Пояснение |
|---|---|
| `unauthorized` | токен отсутствует, просрочен или недействителен |
| `forbidden`, `permission_denied` | недостаточно прав |
| `journals_disabled` | доступ к журналам не предоставлен |
| `role_unsupported` | роль пользователя не поддерживается |
| `invalid_credentials` | неверные почта или пароль |
| `too_many_requests` | слишком много попыток входа |
| `not_found` | объект не найден или недоступен |
| `conflict`, `invalid_status`, `invalid_transition` | действие не подходит текущему состоянию |
| `validation_failed`, `request_invalid` | ошибки данных (`details` — перечень) |
| `record_immutable`, `epl_immutable`, `in_journal`, `already_signed`, `deletion_pending` | запись неизменяема |
| `signing_in_progress` | запись отправлена на подпись |
| `note_not_empty` | примечание мешает подписи |
| `not_record_specialist`, `specialist_mismatch`, `specialist_required`, `specialist_invalid`, `specialist_role_mismatch` | специалист записи |
| `driver_invalid`, `vehicle_invalid` | водитель/ТС не из организации |
| `no_organization`, `not_epl_org` | клиент не привязан к организации или она не на ЭПЛ |
| `record_changed` | запись изменилась после отправки на подпись |
| `record_xml_invalid`, `journal_xml_invalid`, `manifest_xml_invalid` | данные не проходят схему XML |
| `signature_meta_missing`, `storage_integrity`, `document_missing`, `package_missing`, `organization_missing`, `container_invalid` | проблемы сборки журнала (сообщите в поддержку) |

| `no_finisher` | служебный |
