# Эксплуатация и производительность

## Процессы

| Процесс | Команда | Что делает |
|---|---|---|
| API | `uvicorn app.main:app` | HTTP-интерфейс для фронтенда |
| Воркер | `arq app.workers.settings.WorkerSettings` | синхронизация справочников (каждые 5 мин) и задачи подписи (каждые 10 с); оба запускаются и при старте |
| Потребитель | `python -m app.workers.consumer` | читает очередь осмотров RabbitMQ Предрейса |
| Миграции | `alembic upgrade head` | выполняются при каждом развёртывании **до** запуска остальных |

Общее хранилище файлов (`JOURNALS_STORAGE_DIR`) должно быть доступно API, воркеру и потребителю.
Состояние вне БД: Redis (очередь воркера), RabbitMQ Предрейса (только чтение).

## Настройки

Все переменные с префиксом `JOURNALS_`, образец — `.env.example`. Обязательные для боевого запуска:
`DATABASE_URL`, `REDIS_URL`, `STORAGE_DIR`, `PREDREIS_BASE_URL`, `PREDREIS_CLIENT_SECRET`, `RABBITMQ_URL`,
`CORS_ORIGINS`. Рекомендуется задать `EPL_IMPORT_FROM` (дата запуска журнала) и `ORG_SIGNER_USER_ID`
(чьим сертификатом подписывается журнал). **Секрет сервисного клиента хранится только в `.env` на сервере.**

## База данных

- PostgreSQL 16, кодировка UTF-8. Для поиска по ФИО и госномеру нужно расширение `pg_trgm` (миграция 0007 создаёт его
  командой `CREATE EXTENSION IF NOT EXISTS pg_trgm`; в PostgreSQL 13+ оно «доверенное», и хватает прав владельца БД).
- Локаль БД должна уметь регистр кириллицы (`en_US.UTF-8`, `ru_RU.UTF-8` или `C.UTF-8`): от неё зависят
  `ILIKE` и триграммы. Базу в чистой локали `C` (не UTF-8) не использовать.
- Подписанные записи, журнал аудита и электронные документы защищены **триггерами БД**; приложение и миграции
  их не отключают (исключение: одноразовый скрипт исправления данных, см. ниже).

## Резервное копирование

Данные состоят из двух частей, которые нужно копировать **согласованно**: БД (ключи файлов и хеши хранятся в ней)
и каталог файлов `STORAGE_DIR` (XML, PDF, подписи, ZIP). Минимум: ежедневный `pg_dump` (или WAL-архив) и копия
каталога файлов, сделанная сразу после дампа; при восстановлении проверьте хеши командами ниже. Файлы подписанных
документов неизменяемы, поэтому инкрементальное копирование (rsync) безопасно.

## Мониторинг

Проверки живости: `GET /health` (процесс) и `GET /ready` (БД). Запросы для регулярной проверки:

```sql
-- сообщения очереди, которые не удалось превратить в запись (должно быть пусто или стабильно мало)
SELECT reason, count(*) FROM inbox_failures GROUP BY reason ORDER BY 2 DESC;
-- задачи подписи, зависшие дольше обычного
SELECT status, count(*), min(created_at) FROM sign_jobs WHERE status IN ('queued','pending') GROUP BY status;
-- журналы, ожидающие подписи или с ошибкой подписи
SELECT id, status, sign_error FROM e_journals WHERE status IN ('awaiting_signature','signing');
```

Очередь `journal.events.outgoing` в RabbitMQ должна быть близка к нулю. Если она растёт, смотрите журнал потребителя.
В логах нет персональных данных, паролей и токенов; пароль входа не пишется нигде.

## Команды обслуживания

| Команда | Назначение |
|---|---|
| `python -m app.workers.replay [--reason R] [--dry-run]` | повторно обработать сообщения из `inbox_failures` (после синхронизации справочников или правки кода) |
| `python -m app.maintenance.verify_audit` | проверить хеш-цепочку журнала аудита (код возврата 1 — нарушение); безопасно запускать по расписанию |
| `python -m app.maintenance.repair_harmful_factors [--apply]` | одноразово исправить записи «Водителя+» с ошибочным `absent` (по умолчанию только показывает) |
| `python scripts/inspect_signature.py файл` | проверить разбор настоящей подписи (серийный номер, владелец, срок) |

## Производительность

Замеры на синтетических данных: 500 000 медосмотров, 300 000 записей техконтроля, 784 000 документов
(около трёх лет при 1000 записей в сутки), один процессор и 4 ГБ памяти. Абсолютные цифры на боевом сервере будут
лучше, важны отношения. Повторить: `make load-seed && make bench` (на отдельной тестовой БД!).

| Операция | До оптимизации | После |
|---|---|---|
| Список без фильтров, страница 1 | 312 мс | 28 мс |
| Список, страница 2000 | 519 мс | 31 мс |
| Список: организация + месяц | 11 мс | 4 мс |
| Список: только даты | 305 мс | 7 мс |
| Список: подпись «на подпись» у медика | 6 мс | 4 мс |
| Список: «с примечанием» | 207 мс | 2 мс |
| Список: ФИО (полное, ~0,5% таблицы) | 827 мс | 330 мс |
| Список техконтроля: госномер | 313 мс | 159 мс |
| Статистика стартовой | 87 мс | 55 мс |
| **PDF: организация за месяц** | **10,5 с** | **0,44 с** |
| **PDF: ~4800 строк** | **72 с, пик памяти 1,9 ГБ** | **3 с, пик 330 МБ** |
| ZIP: сборка 2000 записей (8000 файлов) | | 0,45 с |

Что дало эффект:

- **PDF** рисуется собственным движком на ReportLab (`app/modules/reports/pdf.py`) вместо HTML→PDF: раскладка считается
  заранее, страницы пишутся потоком. Шрифт DejaVu лежит в репозитории, системные библиотеки не нужны.
- **Фильтр дат** — диапазон по `timestamptz` (границы московских суток), а не выражение «дата по местному времени»:
  только так работает индекс по времени.
- **Индексы** (миграция 0007): по времени (`performed_at DESC, id DESC`), частичный по записям с примечанием,
  триграммные по ФИО водителя и госномеру. Поиск по подстроке записан литералами JSON-пути, а не параметрами, иначе
  PostgreSQL индекс не использует.
- Подстрока в поиске **от 3 символов** (триграммы короче не работают); при выборе водителя или ТС из справочника
  используйте фильтры `driver_id` и `vehicle_id`: они мгновенны.

Известные пределы:

- Выгрузка PDF ограничена 5000 строк (иначе `422`). Журнал на тысячи записей собирается воркером; контейнер ZIP
  формируется в памяти (для 2000 записей это десятки мегабайт), для заметно более крупных журналов понадобится
  потоковая сборка.
- Поиск по частому слову (например, имени, ~10% таблицы) занимает ~250 мс: точный подсчёт всех совпадений.
- Глубокие страницы (смещение в десятки тысяч) быстрые, но при росте базы на порядок стоит перейти на постраничную
  навигацию по ключу.
