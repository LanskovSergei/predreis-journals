# Проверка безопасности перед запуском

Проверка кода сервиса «Электронные журналы» перед выходом с реальными данными. В журналах хранятся данные о
здоровье водителей (особая категория персональных данных) и юридически значимые подписи, поэтому основное
внимание — доступу к чужим данным, утечкам в журналы событий и целостности записей.

**Как проверялось.** Автоматические сканеры: правила безопасности линтера (ruff `S`, они же правила bandit),
`bandit`, `pip-audit`. Ручной разбор: права и доступ к чужим данным подменой идентификатора, вход и токены, журналы
событий, разбор XML, пути файлов, заголовки и CORS, секреты в настройках, ответы на ошибки. Каждая находка
закреплена тестом; ключевые тесты проверены мутацией (падают, если исправление убрать).

## Проверено и подтверждено

- **Доступ к чужим данным (IDOR).** Клиент организации А не видит запись организации Б ни по идентификатору, ни через
  фильтры (`organization_id`, `driver_id`), ни через выгрузку PDF; изменить, удалить, подписать или запросить удаление
  чужой записи нельзя. Ответ на чужую и на несуществующую запись одинаков, по нему нельзя узнать, что запись есть
  (`test_security_access.py`).
- **Матрица прав** по всем ролям сверена с ТЗ и проверена через HTTP (`test_permissions.py`, `test_http_api.py`).
- **Вход.** Пароль передаётся только в Предрейс, не логируется и не хранится; токен проверяется у Предрейса, в кэше
  хранится только его SHA-256; защита от подбора считает неудачи по почте и по адресу; доступ отключается в течение
  30 секунд (`test_security.py`).
- **Ошибки.** Клиенту приходит общий ответ без стека и SQL, подробности — только в логе сервера
  (`test_security_access.py::test_errors_do_not_leak_internals`).
- **Журналы событий.** Строка запроса, тела и идентификаторы записей не пишутся; персональные данные в метках метрик
  не попадают (`test_observability.py`).
- **SQL.** Только через SQLAlchemy с параметрами; строковый SQL есть лишь в миграциях и служебных скриптах и
  собирается из констант.
- **Файлы.** Ключ хранилища не может выйти за каталог хранилища; имена в `Content-Disposition` не содержат
  пользовательского ввода либо закодированы по RFC 5987.
- **Подписанные данные.** Неизменяемость записей типа Б и В, журнала аудита и документов обеспечивают триггеры БД;
  целостность аудита и файлов проверяется командами `verify_audit` и `verify_storage`.
- **Зависимости.** `pip-audit`: известных уязвимостей нет; версии и контрольные суммы зафиксированы, Dependabot включён.
- **Инфраструктура.** Контейнер работает не от root; порты опубликованы только на `127.0.0.1`; метрики по токену с
  сравнением за постоянное время, снаружи закрыты прокси.

## Остаточные риски и рекомендации

Это не ошибки кода, а решения на уровне развёртывания и организации:

1. **Описание API (`/docs`, `/openapi.json`) открыто.** Данных в нём нет, но после запуска фронтенда его стоит
   закрыть на прокси или включать только на стенде.
2. **Ограничение частоты запросов** есть только для входа (в приложении и в шаблоне nginx). Для остальных методов при
   необходимости — на прокси или WAF.
3. **Шифрование данных на диске и в резервных копиях** — на уровне хостинга: для данных о здоровье это требование
   152-ФЗ к площадке. Копии вне сервера хранить зашифрованными.
4. **Выхода из системы на стороне журналов нет:** токен Предрейса живёт 60 минут; отозвать доступ можно в Предрейсе
   (вступает в силу в течение 30 секунд).
5. **Ключи подписи и лицензия у Предрейса:** защищённость подписи определяется их контуром.
6. **Независимый тест на проникновение** перед запуском с реальными данными — рекомендуется.
