# Соответствие реализации техническому заданию

Сверка выполнена по тексту ТЗ «Электронные журналы предрейсовых осмотров» (21 страница) и коду на дату коммита. В колонке «Подтверждение» стоит **имя автоматического теста** (его существование проверяется скриптом при сборке этого документа) либо пояснение. Требования к внешнему виду интерфейса (иконки, цвета, плашки) относятся к фронтенду, здесь проверяется, что API отдаёт для них данные.

**Обозначения:** ✅ реализовано и проверено автоматическим тестом · ☑ реализовано, автоматического теста нет · ◐ реализовано частично · ❌ не реализовано. Колонка «Блокер»: от кого зависит закрытие пункта («—» значит, можно делать без чьего-либо участия).

## Обновление по ответам Предрейса

- **Сертификаты пользователей (F2, F4):** метод `GET /api/v1/service/certificates` готов, в журналах реализованы `GET /me/certificates` и `GET /specialists`. Формат ответа описан словами, образца JSON нет, поэтому имена полей принимаются терпимо и **требуют сверки**. Из 29 записей действующих сертификатов 7, у 22 данных нет (статус `missing`). Серийный номер приходит как `0x…` и приводится к виду из подписи. Отзыв сертификата не проверяется.
- **Метка времени и статус отзыва (B4, B6, C8):** подключение службы штампов времени УЦ и включение проверки отзыва решает заказчик (платная услуга; проверку отзыва можно включить только для журнальных подписей).
- **Формат работы организации (E2, G1):** в Предрейсе такого понятия нет; это связано с вопросом, где заводятся бумажные клиенты (G2, G4, G5; допущения, раздел «Интеграция с Предрейсом», строка 17): предложение Предрейса «только в Предрейсе» противоречит ТЗ, пока бумажные клиенты в нём не заведены.
- **Уведомления (C2, F11, F12):** Предрейс готов отправлять уведомления по запросу журналов, нужен метод и список типов.
- **Вход (E5):** подтверждены способ входа и срок токена 60 минут; роль оператора платформы называется `predreise` (ошибка, из-за которой менеджеры не могли войти, исправлена).
